# 그림자 분신술 — 지능형 병렬 에이전트 오케스트레이션

나루토의 그림자 분신술처럼 각 분신이 독립적으로 작업하고, 소멸 시 기억(결과)이 본체에게 돌아오는 구조.
단순 "에이전트 N개 소환"이 아닌, **정찰 → 분해 → 실행 → 통합** 4단계 파이프라인을 통해 전략적 작업 분해 + 충돌 방지 + 다중 웨이브 + 품질 검증을 수행합니다.

## 사용법

```
/shadow-clone:shadow-clone [에이전트 수] <작업 지시>
```

**예시**:
- `/shadow-clone:shadow-clone 이 프로젝트의 아키텍처를 완전히 분석해줘`
- `/shadow-clone:shadow-clone 5 src/ 전체에서 deprecated API를 찾아 수정해줘`
- `/shadow-clone:shadow-clone 단위테스트, 통합테스트, E2E테스트를 작성해줘`

---

allowed-tools: Bash(git *), Bash(ls *), Bash(wc *), Bash(mkdir *), Bash(rm -rf /tmp/shadow-clone-*), Read, Write, Edit, Grep, Glob, Task, TaskCreate, TaskUpdate, TaskList, AskUserQuestion

---

## !! 필수 준수 사항 !!

**이 워크플로우의 모든 Phase는 반드시 순서대로 실행해야 합니다. 단 하나의 Phase도 건너뛰거나 생략할 수 없습니다.**

절대 하지 말아야 할 것:
- ❌ 정찰(Phase 1)을 건너뛰고 바로 에이전트를 소환하는 것 — 반드시 프로젝트 구조를 먼저 파악하세요
- ❌ 여러 에이전트에게 동일한 파일을 수정하도록 배정하는 것 — **배타적 파일 소유권**을 반드시 지키세요
- ❌ Task 에이전트를 순차적으로 소환하는 것 — 반드시 **단일 메시지에서 병렬로** 소환하세요
- ❌ 에이전트 결과를 검증 없이 그대로 전달하는 것 — 반드시 **통합 & 검증** 단계를 거치세요
- ❌ 에이전트가 작업 계획 md 파일을 생성하지 않는 것 — 각 에이전트는 반드시 **임시 작업 계획 파일**을 생성하고 업데이트하세요

**체크포인트**: 각 Phase 완료 후 다음 Phase로 넘어가기 전에, 해당 Phase가 실제로 실행되었는지 확인하세요.

## 상수 정의

| 상수명 | 값 | 설명 |
|--------|-----|------|
| `MIN_AGENTS` | 2 | 최소 에이전트 수 |
| `MAX_AGENTS` | 10 | 최대 에이전트 수 |
| `WORK_DIR` | `/tmp/shadow-clone-{timestamp}` | 작업 디렉토리 (작업 계획 파일 저장 위치) |
| `PLAN_FILE_PREFIX` | `clone-plan-` | 각 분신의 작업 계획 파일 접두사 |
| `MASTER_PLAN_FILE` | `master-plan.md` | 본체의 마스터 플랜 파일명 |

## 입력 파싱

사용자가 제공한 인자: `$ARGUMENTS`

**파싱 규칙**:
1. 인자 시작 부분에 숫자가 있으면 → 에이전트 수로 사용 (MIN_AGENTS~MAX_AGENTS로 클램프)
2. 숫자가 없으면 → 자동 결정 (Phase 2에서 결정)
3. 숫자 이후의 나머지 텍스트 → 작업 지시

**예시**:
- `5 src/ 전체에서 deprecated API를 찾아 수정해줘` → 에이전트 수: 5, 작업: "src/ 전체에서 deprecated API를 찾아 수정해줘"
- `이 프로젝트의 아키텍처를 분석해줘` → 에이전트 수: 자동, 작업: "이 프로젝트의 아키텍처를 분석해줘"

### Phase 2: 분해 전략 선택 (分解)

**목적**: 정찰 결과를 바탕으로 최적 분해 전략을 결정하고, 각 분신에게 배타적 작업 범위를 할당

**2-1) 분해 전략 결정**:

정찰 결과의 추천 전략을 기반으로, 아래 4가지 전략 중 최적을 자동 선택합니다:

| 전략 | 언제 사용 | 예시 |
|------|----------|------|
| **파일/모듈별** | 독립적 모듈이 명확할 때 | 각 에이전트가 다른 패키지/디렉토리 담당 |
| **관심사별** | 횡단 관심사가 있을 때 | 테스트/타입/로직/스타일 각각 담당 |
| **역할별** | 복합 작업일 때 | 탐색자 + 구현자 + 검증자 |
| **단계별** | 의존성이 있을 때 | 1차: 인터페이스 설계 → 2차: 구현 |

**전략 자동 선택 로직**:
- 작업 대상이 독립적 디렉토리/모듈로 나뉘면 → **파일/모듈별**
- 작업이 "테스트 + 구현" 등 여러 관심사를 포함하면 → **관심사별**
- 작업이 "분석 + 수정 + 검증" 등 복합적이면 → **역할별**
- 작업 결과가 다음 작업의 입력이 되면 → **단계별** (다중 웨이브)

**2-2) 에이전트 수 결정**:

```
입력에 숫자 지정 → 해당 숫자 사용 (2~10 클램프)
숫자 없음 → 자동 결정:
  - 작업 대상 파일/모듈이 7개 이상 → 6~10 (대상 수에 비례)
  - 작업 대상 파일/모듈이 4~6개   → 3~5
  - 작업 대상 파일/모듈이 1~3개   → 2~3
```

**2-3) 배타적 작업 할당**:

각 분신에게 다음을 할당하세요:

| 항목 | 설명 |
|------|------|
| **분신 ID** | `clone-1`, `clone-2`, ... `clone-N` |
| **배타적 파일 소유권** | 해당 분신만 수정 가능한 파일/디렉토리 목록 |
| **작업 범위** | 구체적으로 무엇을 해야 하는지 |
| **기대 출력 형식** | 결과를 어떤 형식으로 반환해야 하는지 |
| **에이전트 타입** | Explore / general-purpose / Bash 중 최적 타입 |

**에이전트 타입 자동 매칭 규칙**:

| 작업 성격 | 에이전트 타입 | 이유 |
|----------|-------------|------|
| 코드 분석, 구조 파악, 검색 | `Explore` | 빠른 탐색에 최적화 |
| 코드 작성, 수정, 리팩토링 | `general-purpose` | 파일 편집 도구 접근 가능 |
| 빌드, 테스트 실행, 스크립트 | `Bash` | 명령어 실행에 특화 |
| 복합 작업 (분석 + 수정) | `general-purpose` | 가장 범용적 |

**2-4) 마스터 플랜 업데이트**:

`$WORK_DIR/master-plan.md`를 업데이트하세요:

```markdown

|---------|-------------|----------|------------|
| clone-1 | {타입} | {영역} | {파일 목록} |

```

### Phase 4: 통합 & 검증 (統合)

**목적**: 모든 분신의 결과를 통합하고, 품질을 검증하여 최종 보고

**4-1) 충돌 감지**:

모든 분신의 결과를 분석하여 다음을 확인:

| 검증 항목 | 방법 |
|----------|------|
| **파일 충돌** | 여러 분신이 동일 파일을 수정했는지 확인 (배타적 소유권이 지켜졌는지) |
| **논리적 충돌** | 한 분신의 변경이 다른 분신의 작업과 모순되는지 확인 |
| **누락된 작업** | 원래 작업 지시 대비 빠진 부분이 없는지 확인 |
| **일관성** | 코딩 스타일, 네이밍 컨벤션 등이 일관적인지 확인 |

**4-2) 충돌 해결** (충돌 발견 시):

충돌이 발견되면:
1. 충돌 내용을 사용자에게 보고
2. AskUserQuestion으로 해결 방향 확인
3. 필요시 추가 에이전트를 소환하여 충돌 해결

**4-3) 품질 검증**:

작업이 코드 수정을 포함하는 경우:
- 수정된 파일들의 구문 오류 여부 확인
- 주요 변경 사항이 의도에 맞는지 스팟 체크

**4-4) 마스터 플랜 최종 업데이트**:

```markdown
## Phase 4: 통합 & 검증
- 충돌: {없음 / N건 발견 → 해결됨}
- 누락: {없음 / N건 발견}
- 품질: {통과 / 이슈 N건}

## 최종 상태: 완료
## 완료 시각: {현재 시각}
```

**4-5) 최종 통합 보고**:

사용자에게 통합된 결과를 보고하세요:

```
## 그림자 분신술 — 임무 완료!

### 투입 전력
- 분신 수: {N}개
- 전략: {전략명}
- 웨이브: {웨이브 수}

### 전체 결과 요약

| 분신 | 상태 | 작업 요약 |
|------|------|----------|
| clone-1 | ✅ | {요약} |
| clone-2 | ✅ | {요약} |
| ... | ... | ... |

### 주요 발견/변경 사항
(모든 분신의 findings를 통합하여 중요도순 정렬)

| 구분 | 파일 | 내용 |
|------|------|------|
| critical | path/file | 설명 |
| warning | path/file | 설명 |
| info | path/file | 설명 |

### 검증 결과
- 파일 충돌: {없음}
- 누락된 작업: {없음}
- 품질 검증: {통과}

### 후속 조치 필요 사항
(있는 경우에만)
- {후속 조치 1}
- {후속 조치 2}
```

**4-6) 작업 디렉토리 정리**:

작업이 완료되면 작업 디렉토리를 정리할지 AskUserQuestion으로 확인:

**질문**: "작업 계획 파일을 보존할까요?"

**옵션**:
1. "삭제" - 임시 파일 정리
2. "보존" - 나중에 참고할 수 있도록 유지

삭제 선택 시:
```bash
rm -rf /tmp/shadow-clone-{timestamp}
```

## 에러 복구

어떤 Phase에서든 에러가 발생하면:

1. `$WORK_DIR/master-plan.md`에 에러 상태를 기록
2. 각 분신의 `clone-plan-{N}.md`에도 현재 상태가 기록되어 있으므로 복구 가능
3. 사용자에게 에러 내용을 보고하고, 재시도 여부를 AskUserQuestion으로 확인

**재시도 시**:
- 마스터 플랜 파일을 읽어서 마지막 성공 Phase부터 재개
- 이미 완료된 분신의 결과는 재사용
- 실패한 분신만 재소환

## 전략별 에이전트 타입 배치 가이드

### 파일/모듈별 전략
```
각 분신 → general-purpose (코드 분석+수정 모두 가능)
별도 검증 분신 → Explore (변경 결과 확인)
```

### 관심사별 전략
```
테스트 담당 → general-purpose (테스트 코드 작성)
타입 담당 → general-purpose (타입 정의 수정)
로직 담당 → general-purpose (비즈니스 로직 수정)
스타일 담당 → general-purpose (린트/포맷팅)
```

### 역할별 전략
```
탐색자(정찰) → Explore (빠른 탐색)
구현자(실행) → general-purpose (코드 작성)
검증자(확인) → Explore 또는 Bash (결과 확인)
```

### 단계별 전략 (다중 웨이브)
```
Wave 1: 설계/분석 → Explore (구조 파악)
Wave 2: 구현 → general-purpose (코드 작성)
Wave 3(선택): 검증 → Bash (테스트 실행)
```
